**DeepGEMM** 是 DeepSeek 开源的一套高性能 GPU 矩阵乘法库，主要面向大模型训练和推理中的低精度计算。

其中 GEMM 是：

> General Matrix Multiplication，通用矩阵乘法  
> 即计算 `C = A × B`，这是 Transformer 大部分计算量的来源。

DeepGEMM 的主要作用是：

- 为低精度矩阵乘法提供高性能 CUDA Kernel。
- 针对 NVIDIA GPU，尤其是 Tensor Core 进行优化。
- 支持大模型常见的普通 GEMM，以及 MoE 模型使用的 grouped GEMM。
- 通过量化、分块、数据布局和流水线优化，提高吞吐量并减少显存带宽压力。

放到你的场景里：

```text
模型权重/激活
      ↓
W8A8 或 W4A8 量化
      ↓
DeepGEMM 执行低精度矩阵乘法
      ↓
得到推理结果
```

例如：

- **W8A8**：8 bit 权重 × 8 bit 激活。
- **W4A8**：4 bit 权重 × 8 bit 激活。
- DeepGEMM 负责尽可能高效地执行这些矩阵乘法，但量化、缩放因子计算和精度校准通常还需要上层推理框架配合。

需要注意：DeepGEMM 最初最有代表性的能力是 **FP8 GEMM**。你看到的“W4A8（DeepGEMM）”可能意味着项目在 DeepGEMM 基础上新增了 4-bit 权重解码或自定义 Kernel，不一定是原版 DeepGEMM 开箱即用的标准能力。

简单说，**量化方案决定“用什么精度算”，DeepGEMM 负责“在 GPU 上尽量算得快”**。

### 15. assistant · 2026-08-26T03:48:56.513Z

来源: `sessions/2026/08/23/rollout-2026-08-23T02-46-28-01a02c83-281d-7751-95f7-678490ab1c02.jsonl:95`

这里的 **MegaMoE** 不是某个模型名称，而是 DeepGEMM 中针对超大规模 **MoE（混合专家模型）**设计的一种融合计算方案。

普通 MoE 层大致依次执行：

```text
路由选专家
→ 把 token 分发到不同 GPU/专家
→ 第一层矩阵乘法
→ SwiGLU 激活
→ 第二层矩阵乘法
→ 把各专家结果传回并合并
```

MegaMoE 将这些步骤融合为一个大型 GPU kernel：

```text
EP Dispatch
→ Linear 1（FP8 × FP4）
→ SwiGLU
→ Linear 2（FP8 × FP4）
→ EP Combine
```

其中：

- **EP** 是 Expert Parallelism，即专家并行。
- 专家分布在多张 GPU 上。
- MegaMoE 会尽量让 **NVLink 通信与 Tensor Core 计算重叠进行**，减少等待和中间数据搬运。
- 权重采用 FP4，输入激活通常采用 FP8，最终输出可以是 BF16。

所以“**跑通 FP4 MegaMoE**”通常表示：

> 已经让 FP4 权重版本的 MegaMoE 融合算子能够在多卡环境完成端到端运行，包括 token 路由、跨卡通信、两个专家线性层、SwiGLU 和结果合并。

但“跑通”通常只说明基本功能链路成功，未必意味着已经：

- 完成数值精度验证；
- 达到理想性能；
- 覆盖所有 batch、token 数和模型配置；
- 集成到完整模型推理；
- 通过长时间稳定性测试。

另外，称为“FP4 MegaMoE”也不代表整个模型都以 FP4 计算。更准确地说，一般是 **MoE 专家层权重为 FP4，激活为 FP8，即 FP8 × FP4 GEMM**，路由、缩放因子、累加和输出仍可能使用其他精度。

## 部署结构

大致是：

```text
客户端 / Benchmark
        ↓
PD Router
   ┌────┴────┐
Prefill 服务  Decode 服务
4 张 GPU      8 张 GPU
PP=4          TP=8、DP Attention=8
端口 8010     端口 8055
```

链接里的 `2p1d` 很可能表示：

- 2 个 Prefill 实例
- 1 个 Decode 实例

但你贴出的内容只展示了一条 Prefill 启动命令，可能这条命令会在两台机器上分别启动。

### Prefill 服务

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
sglang serve \
  --model-path /data1/model/DeepSeek-V4-Flash-0731 \
  --pp-size 4 \
  --chunked-prefill-size 16384 \
  --disaggregation-mode prefill
```

含义：

- 使用 GPU 0～3，共 4 张卡。
- `--pp-size 4`：模型按流水线并行切到 4 张卡。
- `--chunked-prefill-size 16384`：长输入每次最多分块处理 16384 token，减少单次 Prefill 峰值压力。
- `--disaggregation-mode prefill`：这套服务只负责处理输入提示词和生成 KV Cache，不负责持续生成输出 token。
- `--mem-fraction-static 0.80`：约 80% 显存用于模型权重、KV Cache 等静态内存池。
- `--port 8010`：监听 8010 端口。

### Decode 服务

```bash
sglang serve \
  --model-path /data1/model/DeepSeek-V4-Flash-0731 \
  --tp 8 \
  --dp 8 \
  --enable-dp-attention \
  --enable-dp-lm-head \
  --chunked-prefill-size 32768 \
  --moe-runner-backend flashinfer_mxfp4 \
  --cuda-graph-backend-decode full \
  --cuda-graph-max-bs-decode 400 \
  --max-running-requests 400 \
  --speculative-algorithm DSPARK \
  --speculative-attention-mode decode \
  --disaggregation-mode decode \
  --port 8055
```

重点参数：

- `--tp 8`：FFN/MoE 等计算使用 8 卡张量并行。
- `--dp 8 --enable-dp-attention`：Attention 使用数据并行；在这种模式下，SGLang 要求 DP 和 TP 大小相等。
- `--enable-dp-lm-head`：对最终词表输出层做并行，减少 DP 组之间的全量聚合。
- `flashinfer_mxfp4`：使用 FlashInfer 的 MXFP4 MoE 计算后端。
- `cuda-graph ... full`：对 Decode 批次捕获完整 CUDA Graph，降低 kernel launch 开销。
- `cuda-graph-max-bs-decode 400`：CUDA Graph 最大覆盖到 decode batch size 400。
- `max-running-requests 400`：最多同时维护 400 个运行中请求。
- `DSPARK`：使用 DSPARK 推测解码，一次推测多个 token，再由主模型验证。
- `disaggregation-mode decode`：只负责逐 token 解码，从 Prefill 服务接收 KV Cache。

需要特别注意：这里用的是：

```text
--moe-runner-backend flashinfer_mxfp4
```

它表示 **MXFP4 的 MoE 矩阵计算后端**，并不等同于前面提到的 MegaMoE。若明确使用 MegaMoE 通信融合后端，通常还会看到：

```text
--moe-a2a-backend megamoe
```

你贴出的命令里没有这个参数，因此这份测试不能直接称为“MegaMoE 测试”。

## 表格怎么看

每一行对应一种输入长度和并发规模。列可以还原成：

| 指标 | 含义 |
|---|---|
| Input length | 每个请求的输入 token 数 |
| Output length | 计划生成的输出 token 数 |
| Successful requests | 成功完成的请求数量 |
| Max request concurrency | 压测客户端设置的最大并发数 |
| Mean/Median/P95/P99 TTFT | 首 token 延迟 |
| Mean/Median/P95/P99 TPOT | 后续每个输出 token 的平均耗时 |
| Request throughput | 每秒完成请求数 |
| Input token throughput | 每秒处理的输入 token 数 |
| Input token throughput per GPU | 输入吞吐除以 8 张 Decode GPU |
| Output token throughput | 每秒生成的输出 token 数 |
| Output token throughput per GPU | 输出吞吐除以 8 张 Decode GPU |

### TTFT

TTFT 是 Time To First Token，从请求发出到拿到第一个输出 token。

它通常包含：

```text
排队时间 + Prefill 计算 + KV Cache 传输 + Decode 首 token
```

越小越好。高并发时排队加重，所以 TTFT 会明显上升。

### TPOT

TPOT 是 Time Per Output Token，首 token 之后，每生成一个 token 的平均耗时。

例如：

```text
TPOT = 20 ms
```

大约相当于单条生成流每秒：

```text
1000 / 20 = 50 token/s
```

但这是单请求的生成速度，不等于服务器所有请求合计吞吐。

## 结果反映了什么

以 8192 输入、1024 输出为例：

| 并发 | 平均 TTFT | P99 TTFT | 平均 TPOT | 输出吞吐/GPU |
|---:|---:|---:|---:|---:|
| 1 | 1.64 s | 1.64 s | 15.20 ms | 7.44 tok/s |
| 32 | 4.77 s | 10.33 s | 20.19 ms | 143.82 tok/s |
| 128 | 11.11 s | 30.74 s | 30.52 ms | 354.41 tok/s |
| 256 | 15.96 s | 57.54 s | 45.45 ms | 483.79 tok/s |

说明：

- 增大并发可以显著提高总吞吐量。
- 代价是单请求的首 token 延迟和生成延迟变高。
- 8192 输入在并发 128～256 时，Decode 已经出现较明显的拥塞。

长输入下更加明显：

- 输入 51,200、并发 1：平均 TTFT 约 **5.34 秒**。
- 输入 204,800、并发 1：平均 TTFT 约 **16.58 秒**。
- 输入 204,800、并发 32：平均 TTFT 约 **182.88 秒**。
- 输入 204,800、并发 64：平均 TTFT 约 **282.59 秒**。

这说明超长上下文高并发时，主要问题已经不是单步 Decode，而是：

```text
Prefill 计算
+ 请求排队
+ KV Cache 占用/传输
```

值得注意的是，204,800 输入、并发 64 的最后一行，`request throughput=0.20 req/s`，但 `output throughput=27.75 tok/s`，与固定输出 1024 token 不太匹配。可能有：

- 请求提前遇到 EOS；
- 部分输出被截断；
- 压测超时；
- 表格复制错位；
- Output length 只是最大输出长度，并非实际平均长度。

因此最后一行最好回到 benchmark 页面检查实际生成 token 数和失败/截断统计。

整体结论是：**这套 2P1D、4 卡 Prefill + 8 卡 Decode 的 MXFP4 部署可以处理最长约 20 万 token 的输入；并发提高会增加吞吐，但长上下文下 TTFT 急剧上升，Prefill/排队逐渐成为主要瓶颈。**

这是 **PD 分离（Prefill-Decode Disaggregation）**，不是 PD 聚合。

最明确的证据是启动了两个不同角色的服务：

```bash
# 只做 Prefill
--disaggregation-mode prefill
--port 8010

# 只做 Decode
--disaggregation-mode decode
--port 8055
```

而链接里的 `2p1d` 很可能代表 **2 个 Prefill 实例 + 1 个 Decode 实例**。

## 两者的区别

### PD 聚合

同一个 SGLang 实例、同一组 GPU 同时执行 Prefill 和 Decode：

```text
请求
  ↓
同一组 GPU
  ├─ Prefill：处理完整输入
  └─ Decode：逐 token 生成
```

启动时通常不设置：

```bash
--disaggregation-mode prefill
--disaggregation-mode decode
```

优点：

- 部署简单。
- 不需要跨实例传输 KV Cache。
- GPU 数量较少时更容易使用。
- 中低负载下通常有不错的延迟。

缺点：

- Prefill 是计算密集型的大任务，可能阻塞 Decode。
- Decode 需要稳定、低延迟的小步计算，容易被长提示词干扰。
- 长上下文或突发请求容易造成 TPOT 抖动。
- Prefill 和 Decode 无法分别独立扩容。

### PD 分离

使用不同实例或不同 GPU 分别运行两个阶段：

```text
请求
  ↓
Prefill GPU
  │ 计算输入并产生 KV Cache
  ↓ 跨卡/跨机传输 KV Cache
Decode GPU
  │ 逐 token 生成
  ↓
输出
```

你的配置大致是：

```text
2 个 Prefill 实例：每个 PP=4
          ↓ KV Cache
1 个 Decode 实例：TP=8、DP Attention=8
```

优点：

- 长输入 Prefill 不容易打断 Decode。
- Decode 的 TPOT 更稳定。
- Prefill 和 Decode 可以分别调并行策略。
- 可以根据业务比例独立扩容，比如从 `2P1D` 调成 `3P1D` 或 `2P2D`。
- 特别适合长上下文、高并发和在线推理。

缺点：

- 必须传输 KV Cache，可能需要 NVLink、RDMA、Mooncake 或 NIXL 等高速传输方案。
- 部署、服务发现和请求路由更复杂。
- Prefill/Decode 数量配置不合理时，一边可能空闲，另一边排队。
- 短输入场景下，KV 传输开销可能抵消分离收益。

## 一句话判断

```text
没有指定 disaggregation mode
→ 通常是 PD 聚合

分别启动 prefill 和 decode 服务
→ PD 分离
```

你的命令明确属于后者。这里的“聚合”并不是把多个 P/D 实例放到一个路由器后面；即使前面有统一入口，只要 Prefill 和 Decode 运行在不同服务/GPU 上，仍然属于 **PD 分离**。

“运行 Recipe”就是一份经过实际验证的**模型部署操作手册**。

这里的 Recipe 不是模型代码，也通常不要求开发新算子。它要回答一个具体问题：

> 如何在硬件 Y 上，用 vLLM-Omni 跑通模型 X，完成任务 Z？

例如：

```text
模型：Ovis-Image
硬件：1× H100 80GB
任务：文生图
框架：vLLM-Omni
```

对应的 Recipe 会是一份 Markdown 文档，例如：

```text
recipes/OvisAI/Ovis-Image.md
```

一般需要包含：

- 测试过的 GPU 型号、数量和显存；
- 操作系统、Python、CUDA、PyTorch、vLLM-Omni 版本；
- 模型下载和依赖安装方式；
- 完整启动或推理命令；
- 验证请求、Prompt 或脚本；
- 实际生成的图片、音频、视频或日志；
- 峰值显存、延迟、吞吐等数据；
- 已知限制和常见问题。

比如文生图 Recipe 可能包含：

```bash
vllm-omni serve OvisAI/Ovis-Image \
  --tensor-parallel-size 1 \
  --port 8000
```

然后提供验证方式：

```bash
curl http://localhost:8000/v1/images/generations \
  -H "Content-Type: application/json" \
  -d '{
    "model": "OvisAI/Ovis-Image",
    "prompt": "A red panda reading a book"
  }'
```

再记录：

```text
硬件：1× H100 80GB
成功输出：output.png
峰值显存：约 xx GiB
生成耗时：约 xx 秒
分辨率：1024×1024
限制：暂不支持多请求并发
```

核心要求是**必须亲自在申报的硬件上端到端跑通**。仅根据官方 README 拼接命令，或者没有真实验证输出的文档，通常不会被接受。

因此这个 issue 中的任务主要是：

```text
安装和部署模型
→ 找到正确配置
→ 实际运行并验证
→ 记录性能与限制
→ 把过程整理成可复现文档
→ 提交 Recipe PR
```

虽然主要产物是文档，但过程中如果发现小问题，也可能需要顺便修复示例脚本、参数、依赖或文档链接。

在 Mooncake 里，`master` 通常指 **Mooncake Store 的中心控制服务（Master Service）**，不是模型推理里的主 GPU，也不是 Prefill 主节点。

它主要负责：

- 维护集群中有哪些存储节点；
- 记录 KV Cache/Object 存在哪些机器、哪些内存段；
- 为新对象分配存储位置；
- 管理副本、容量、淘汰和节点上下线；
- 向客户端返回对象的位置元数据。

实际数据不会经过 Master：

```text
客户端 A ──查询位置──> Mooncake Master
客户端 A <──对象位置── Mooncake Master

客户端 A ═══ RDMA/TCP 直接传输数据 ═══> 客户端 B
```

因此 Master 是“控制面”，数据通过 Transfer Engine 在节点间直接传输。

## 与 Metadata Service 的区别

Mooncake 中还有一个容易混淆的 `metadata server`：

| 组件 | 作用 |
|---|---|
| Mooncake Master | 管理 Mooncake Store 的对象位置、空间分配、副本和淘汰 |
| Metadata Service | 给 Transfer Engine 提供节点发现、网卡和内存注册信息 |
| Transfer Engine | 真正通过 TCP/RDMA 搬运数据 |
| Store Client | 发出 Put/Get 请求，并可贡献 DRAM/VRAM/SSD 空间 |

例如客户端初始化可能同时需要：

```python
store.setup(
    metadata_server="P2PHANDSHAKE",
    master_server_addr="10.0.0.1:50051",
    ...
)
```

这里：

- `metadata_server` 服务 Transfer Engine；
- `master_server_addr` 指向 Mooncake Store Master；
- 两者不是一个东西。

## 你之前的 SGLang PD 场景可能不需要 Master

SGLang 的：

```bash
--disaggregation-transfer-backend mooncake
```

通常使用的是 **Mooncake Transfer Engine**，让 Prefill 节点直接把 KV Cache 传到 Decode 节点：

```text
Prefill GPU ──Mooncake Transfer Engine/RDMA──> Decode GPU
```

这种纯 PD 传输模式可以不部署 Mooncake Store，自然也不需要 `mooncake_master`。SGLang Router 负责 P/D 请求调度，bootstrap 服务协调本次 KV 传输。

只有使用以下类型的能力时，通常才涉及 Mooncake Store Master：

- Mooncake Store Connector；
- 跨请求共享 KV Cache；
- HiCache/分布式 KV 存储；
- Put/Get/Remove 对象存储；
- DRAM/SSD 缓存池；
- 副本、淘汰和持久化管理。

一句话概括：

> **Mooncake Master 是分布式缓存的“目录和空间调度中心”，不搬数据；纯 Mooncake Transfer Engine 的 PD 分离通常不需要它。**

## 为什么 FP4 看起来“不受支持”

GLM‑5.3‑Flash 不是普通的稠密文本模型，它包含：

- MoE 专家层；
- GLM sparse MLA/KDA；
- 视觉模块；
- fused QKV 等融合层；
- NextN/MTP 推测解码层；
- 一部分必须保持 BF16 的混合精度模块。

因此不仅要有 FP4 GEMM kernel，还必须保证：

```text
量化配置识别
→ mixed-precision exclusion
→ fused layer 名称映射
→ FP4 权重加载
→ MoE kernel
→ sparse attention / KDA
→ MTP/NextN
→ 多卡 TP/EP
```

任何一层没适配好，都可能在加载或推理阶段失败。

## SGLang 当前已知的两个 NVFP4 问题

### #36596：混合精度排除规则失效

[SGLang #36596](https://github.com/sgl-project/sglang/issues/36596)

GLM‑5.3‑Flash 的 NVFP4 checkpoint 会把一些敏感层保留为 BF16，但 SGLang 的 `ModelOptFp4Config.is_layer_excluded()` 没有正确匹配：

- checkpoint 中的单投影名称与运行时 fused module 名称；
- 带 `model.` 前缀和重命名后的模块名称。

结果是：

```text
checkpoint：该层是 BF16
SGLang：错误地创建成 FP4 packed layer
→ 加载时 shape mismatch
```

报告者提供了可行补丁，并声称修复后可以加载全部120个 shard。

### #36599：量化 NextN/MTP 加载失败

[SGLang #36599](https://github.com/sgl-project/sglang/issues/36599)

SGLang 的 DeepSeek NextN 公共路径对 `modelopt_fp4` 强制执行：

```python
quant_config = None
```

这对 MTP 仍为 BF16 的 DeepSeek checkpoint 是合理的，但部分 GLM‑5.3‑Flash NVFP4 checkpoint 连 NextN 层也量化了。于是：

```text
运行时创建 BF16 NextN
checkpoint 保存 FP4 NextN
→ 专家权重 shape mismatch
```

如果不启用 NextN/MTP 推测解码，这个问题可能暂时不会触发，但不能认为功能完整。

## 你的机器适合哪条路线

你的机器是：

```text
8×RTX PRO 5000 Blackwell 72GB
SM120
```

这正是 NVFP4 的目标硬件，比较推荐两种路线：

### 想先稳定跑通

优先尝试：

```text
RedHatAI/GLM-5.3-Flash-NVFP4
+ vLLM
+ compressed-tensors
```

先关闭：

- MTP/NextN；
- 多模态输入；
- 复杂 CUDA Graph；
- 长上下文；
- Prefix Cache。

先验证纯文本、短上下文，再逐项打开功能。

### 想使用 SGLang

可以尝试：

```text
LibertAIDAI/GLM-5.3-Flash-NVFP4
+ SGLang ModelOpt FP4
+ Marlin MoE backend
```

但可能需要 #36596 的补丁；启用 NextN 时还可能需要 #36599 的修复。它目前更像“社区正在打通”，而不是官方稳定支持。

## 这也可能是不错的贡献机会

你的 SM120 八卡环境很适合帮助完善 GLM‑5.3‑Flash NVFP4：

1. 在未修改的 SGLang main 上复现 #36596。
2. 应用建议修复，验证全部权重加载。
3. 测试纯文本、视觉输入和并发隔离。
4. 再验证 #36599 的量化 NextN。
5. 比较：
   - FP8 与 NVFP4 显存；
   - 吞吐和 TPOT；
   - TP/EP 组合；
   - MTP 开关前后收益；
   - 精度回归。

不过 #36596 的报告者已经写了 “Happy to turn this into a PR”，所以如果想参与，应该先在 issue 中询问是否可以负责 SM120 八卡验证或共同提交，不要直接重复写补丁。

结论：**社区有 GLM‑5.3‑Flash FP4，尤其是 NVFP4；但 SGLang 的混合精度层匹配和量化 MTP 仍有开放问题。你的 PRO 5000 非常适合跑 NVFP4，只是目前可能需要补丁，尚不是完全开箱即用。**
