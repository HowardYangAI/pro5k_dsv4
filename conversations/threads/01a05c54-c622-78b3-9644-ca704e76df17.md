### 2. 第一段实习：低比特 KV Cache

主要工作是给生成阶段的 Attention 推理链路做 KV Cache 量化优化。

- **问题背景**：大模型生成时需要不断读取历史 K/V。上下文越长，KV Cache 占用的显存和访存带宽越大，容易成为推理瓶颈。
- **解决思路**：
  - 用 Triton 重写 QK、PV Kernel；
  - 在寄存器内完成 Compact 数据展开；
  - 复用量化所需的 Scale/Zero；
  - 使用 Bit-pack 压缩存储；
  - 按 GEMV 访问特点重新设计 Cache 布局和显存预分配。
- **结果**：
  - 端到端加速 4.6×；
  - 吞吐提升 3.8×；
  - QK/PV Kernel 分别提升 6.7×、2.1×；
  - 量化阶段提升约 1.79—1.81×；
  - 临时显存降低 90.8%—94.9%；
  - 指标误差控制在 `5e-4` 内。

这段非常亮眼，因为同时覆盖了算法、数据布局、Kernel 实现和端到端验证。不过面试官很可能追问：

- 4.6× 的 baseline 是什么？

- 是否包含量化、反量化和数据转换开销？

### 3. 第二项：FlashKDA 算子优化

这是面向超长序列的线性/递归注意力算子优化。

- **任务规模**：总计约199万 token 的变长负载。
- **核心方法**：
  - 将 K2 递推状态跨 Chunk 保存在寄存器中；
  - 用重计算替代 Q/K/G 中间量的显存读写；
  - 调整 CTA 调度和 `launch_bounds`；
  - 降低 `mio_throttle`，消除寄存器溢出。
- **结果**：
  - 前向延迟从 78.65 ms 降至约36 ms，提升2.19×；
  - 工作区显存从13.81 GB 降至1.18 GB，减少约91.5%；
  - 保持逐比特一致。

这里体现了比较扎实的 GPU 性能分析能力：

- 知道在计算和访存间做权衡；
- 能处理寄存器压力、occupancy、spill、CTA 调度；
- 会通过 profiler 指标定位瓶颈；
- 不只追求速度，还验证数值一致性。

潜在疑点是“总计199万 token”非常大，需要说明它是 batch 内 token 总量、合成 benchmark，还是单序列长度。“逐比特一致”也可能被追问：与哪一个实现一致、使用什么数据类型、不同 GPU 上能否保证。

### 4. 第三项：Attention 分析工具

- 通过 replay 相同的 Q/K/V，获取 `softmax_lse`；
- 重建 Attention Probability；
- 同时保留原生 FlashAttention 前向过程；
- 在 Qwen3-0.6B 的28层测试中，LSE 最大误差为 `1.14e-5`。

这项工作的价值在于：FlashAttention 通常不会显式保存完整 Attention Matrix，因为那会带来很大的显存开销。该工具可以用于：

- 分析模型到底关注哪些 token；
- 对比不同 Attention 实现；
- 排查精度漂移；
- 验证量化或算子改写是否正确。

不过简历里需要进一步说明工具的使用场景，以及是否会产生 \(O(n^2)\) 的显存或计算开销。单写误差值，业务价值稍弱。

## 1. 低比特 KV Cache：方向高度已有，Kernel 实现可能有增量

简历内容：

- KV Cache 低比特量化；
- Scale/Zero；
- Bit-pack；
- 寄存器内 Compact 展开；
- 重写 QK/PV Kernel；
- 设计 GEMV-native Cache 布局；
- 降低临时显存。

开源社区已有大量先行工作：

- [KVQuant](https://arxiv.org/abs/2401.18079)：KV Cache 低比特量化、异常值处理和长上下文。
- [KIVI](https://arxiv.org/abs/2402.02750)：非对称低比特 KV Cache，讨论 K/V 不同量化粒度。
- [GEAR](https://arxiv.org/abs/2403.05527)：通过量化及低秩/稀疏校正压缩 KV Cache。
- [QServe](https://arxiv.org/abs/2405.04532)：W4A8KV4 推理，包含低比特 KV 存储和面向 GPU 的执行优化。
- vLLM、TensorRT-LLM、FlashInfer 等框架也已经支持或持续开发 FP8/INT8/更低位 KV Cache。

### 重合程度

- **算法方向：高重合**
- **Bit-pack、Scale/Zero、融合反量化：高重合**
- **针对特定硬件和形状重写 Triton QK/PV：可能有增量**
- **GEMV-native Cache 布局：可能有较强工程创新**

“在寄存器内解包、复用 scale/zero、避免中间显存、融合进 Attention Kernel”本身是低比特 Kernel 的常见优化路线，不宜包装成原创思想。

但工程实现仍可能有价值，因为不同模型、位宽、GPU、head dimension、GQA 配置需要不同的数据布局与 Kernel 调度。真正需要确认的是：

- 相比 KIVI、KVQuant、QServe 或框架原生实现，新增点是什么？
- 支持的是 INT2、INT4、FP4 还是其他格式？
- 是第一次实现该格式，还是重写现有 Kernel？
- baseline 是否已经融合反量化？
- 代码有没有提交到公开仓库？

### 判断

属于：

> 已有算法方向 + 针对特定负载的高质量 Kernel 工程优化。

不能称为全新算法，但也不能仅因社区已有 KV 量化就认定是无意义重复。

## 3. Attention 分析工具：原理基本是已有方法

简历内容：

- replay 相同 Q/K/V；
- 获取 `softmax_lse`；
- 重建 Attention Probability；
- 保留原生 FlashAttention 前向。

这在数学上是直接重建：

\[
S = QK^\top \cdot scale + mask
\]

\[
LSE_i = \log \sum_j e^{S_{ij}}
\]

\[
P_{ij} = e^{S_{ij}-LSE_i}
\]

FlashAttention 官方接口早就具有：

- `return_softmax_lse`
- `return_attn_probs`

官方测试代码也会用普通 PyTorch Attention 作为 reference，对输出、LSE 或概率进行比较。TransformerLens、BertViz、各类 Attention 可视化工具同样会通过 hook 或重新执行注意力来获得概率矩阵。

### 重合程度

- **数学方法：完全已有**
- **Q/K/V replay：常规调试办法**
- **LSE 验证：FlashAttention 官方测试已有**
- **在 Qwen3 与生产 FlashAttention 路径中的工具集成：可能有工程价值**

它的价值更可能是：

- 不替换线上 FlashAttention；
- 自动抓取每层 Q/K/V；
- 正确处理 RoPE、GQA、causal mask、padding、varlen；
- 将重建结果和线上 LSE 对齐；
- 支持分层分析与误差定位。

### 判断

属于：

> 调试与可观测性工具，不属于新算法。

## 1. K1/K2 划分确实完全已有

公开初版已经把 FlashKDA 拆成：

- K1：处理 gate、归一化、decay、矩阵构造和求逆；
- K2：逐 Chunk 执行 recurrence、输出投影和状态更新。

公开文档甚至明确说明：

> 早期单 Kernel 方案并行度不足，拆成 K1/K2 后端到端至少提升15%。

所以，如果候选人把“K1/K2 拆分”当作自己的设计，这是不成立的。

但截图中的简历似乎没有直接宣称“由本人提出 K1/K2 拆分”，而是说“将 K2 递推状态跨 Chunk 保留于寄存器”。这两者不是同一件事。

## 2. “状态跨 Chunk 保留于寄存器”不是公开初版已有实现

公开初版 K2 中的递推状态叫 `state_acc`，代码将它定义在 shared memory：

```cpp
alignas(128)
cute::ArrayEngine<BF16, ...> state_acc;
```

其执行结构大致是：

```text
加载初始 state
        ↓
放入 shared-memory state_acc
        ↓
遍历多个 Chunk
        ↓
每个 Chunk 读取/更新 state_acc
        ↓
写出 final state
```

所以公开初版虽然已经“让递推状态跨 Chunk 存活”，但它的主要驻留位置是 shared memory，不是寄存器。

简历宣称的新方案则可能是：

```text
加载初始 state
        ↓
拆分给各线程的寄存器 fragment
        ↓
跨多个 Chunk 始终保留在寄存器
        ↓
最后才写回
```

这会减少每个 Chunk 对 shared memory 的反复访问和同步。如果状态真的是在多个 Chunk 之间一直分布式驻留于各线程寄存器，那么它是相对于公开初版的实质性重构。

需要注意一个表述陷阱：

- “状态跨 Chunk 保留”是 KDA 递推本身必然要求的；
- “状态跨 Chunk 保留在寄存器，而不是 shared memory”才是具体优化贡献。

面试时必须让候选人明确说出后者。

## 3. “用重计算替代中间量访存”很可能是真正的核心优化

公开初版 K1 会产生并写入全局 Workspace 的中间量包括：

- `k_decayed`
- `q_decayed`
- `k_restored`
- `g_total`
- `INV`
- `Mqk`

随后 K2 再从 Workspace 读取这些数据。

也就是说，公开初版的结构是：

```text
K1 计算派生量
    ↓
6 类数据写入全局 Workspace
    ↓
K2 从 Workspace 重新读入
    ↓
执行 recurrence
```

这正是简历所谓“Q/K/G 中间量访存”的可能来源。这里的“Q/K/G 中间量”大概率不是原始 Q、K、G，而是：

- 经过 decay 的 Q；
- 经过 decay 的 K；
- restored K；
- gate 的累计或总量。

简历的新方案很可能改为：

```text
只存必须跨 Kernel 保存的小矩阵
        ↓
K2 读取原始量或少量必要数据
        ↓
在 K2 内重新计算 Q/K/G 派生量
        ↓
避免存取大体积中间张量
```

这是经典的“以计算换显存带宽”，但在该公开初版中并没有这样实现。

## 4. 显存数字能够支持这个推断

设 `CHUNK=16`、`D=128`、BF16 为2字节。公开初版每个 Chunk/Head 的主要 Workspace 大约是：

| 中间量 | 大小 |
|---|---:|
| `k_decayed [16,128]` | 4096 B |
| `q_decayed [16,128]` | 4096 B |
| `k_restored [16,128]` | 4096 B |
| `g_total [128]`，FP32 | 512 B |
| `INV [16,16]` | 512 B |
| `Mqk [16,16]` | 512 B |
| 合计 | 13,824 B |

前三个大矩阵就占了12,288 B。

假设优化后只保留 `INV` 和 `Mqk`：

\[
\frac{1024}{13824}\approx 7.4\%
\]

即理论上减少约：

\[
92.6\%
\]

简历报告：

- 13.81 GB → 1.18 GB；
- 减少约91.5%。

两者非常接近。考虑对齐、元数据和额外 buffer 后，这个数字很合理。

因此，简历中的显存下降不像是随便写的，它与“删除 Q/K/G 大型 Workspace 中间量，只保留小矩阵”的代码结构高度吻合。

这至少在技术逻辑上表明，它描述的不是简单复述公开 Deep Dive。

## 5. `launch_bounds` 是已有手段，但调优结果可能是新的

公开初版 K1 已经有类似：

```cpp
__launch_bounds__(NumThreads, 8)
```

文档也明确写到，它为了提高 occupancy，接受了少量寄存器 spill。

所以：

- 首次使用 `launch_bounds`：不是候选人创新；
- 重新调整线程数、最小 block 数、寄存器分配：可以是新工作；
- 配合状态寄存器化之后重新平衡 occupancy：很可能是必要的新工作。

因为将完整递推状态移入寄存器，会明显增加寄存器压力，可能导致：

- 每个线程寄存器数过多；
- active CTA 数下降；
- occupancy 下降；
- register spill 到 local memory；
- 性能反而变差。

因此必须结合：

- CTA 划分；
- 每个线程持有的 state fragment；
- `launch_bounds`；
- pipeline stage 数量；
- warp 职责；

一起调优。

所以这里更准确的评价是：

> `launch_bounds` 方法已有，但在新的寄存器驻留方案下重新找到不 spill 的配置，可能是实质性工程贡献。

## 6. `mio_throttle` 从30.6%降到9.7%意味着什么

`mio_throttle` 通常表示 warp 因 MIO 管线资源不足而无法发射。相关操作可能包括：

- shared-memory load/store；
- 某些特殊功能单元指令；
- 寄存器与 shared memory 之间的数据搬运；
- 部分转换或数据组织指令。

公开初版大量依赖：

- shared-memory `state_acc`；
- 中间数据的 shared-memory staging；
- K1 写 Workspace、K2 再加载；
- 多阶段同步和转置。

如果新版本：

- 将递推状态放在寄存器；
- 减少 shared-memory round trip；
- 重计算部分数据；
- 改善 CTA/warp 的流水线安排；

那么 `mio_throttle` 从30.6%降至9.7%是符合预期的。

不过这个指标本身不是创新，它只是 profiling 证据。真正有价值的是：

> 候选人是否通过 profiler 定位到 MIO 压力，并设计了能减少相关指令和同步的实现。

## 7. “消除寄存器溢出”与公开初版形成明确差异

公开初版文档明确说：

> 通过 `__launch_bounds__(256, 8)`，有意接受少量 register spilling，以换取更高的每 SM block 数。

简历则声称最终“消除寄存器溢出”。

这说明两者不是完全相同的实现目标：

- 公开初版：允许少量 spill；
- 简历版本：在新调度或寄存器分配方案中消除 spill。

但需要警惕：寄存器状态驻留通常会增加寄存器压力，按直觉更容易 spill。候选人必须解释他如何同时做到：

- 把更大状态放入寄存器；
- 又消除 spill；
- 还保持足够 occupancy。

合理方案可能包括：

- 改变 CTA 线程数；
- 将状态分片给更多线程；
- 缩短部分临时变量生命周期；
- 分离 load/compute warp；
- 复用寄存器；
- 调整 pipeline stage；
- 通过重计算减少同时存活的中间值；
- 调整 `launch_bounds` 的第二参数。

如果只能回答“调了 `launch_bounds`”，可信度不够。
