这个开关的实际含义是：

> 给每个请求伪造 `bootstrap_host=2.2.2.2`，让 SGLang 把该请求的 KV Cache 传输后端切换成 `FAKE`，从而跳过真实的 P-D 网络 KV 传输，但保留完整的请求、握手、轮询和调度流程。

参数完整名称是：

```text
--enable-test-pd-without-transfer
```

你贴出的 `without-transfe` 应该是少了最后一个 `r`。

## 1. 请求端做了什么

Benchmark 代码在 [bench_serving.py:1906](/sgl-workspace/llm-benchmark-online/bench_serving.py:1906) 附近注入：

```python
extra_request_body["bootstrap_host"] = "2.2.2.2"
extra_request_body["bootstrap_room"] = "0"
```

实际发送每个请求时，还会重新生成一个随机的 `bootstrap_room`：

```python
new_extra_request_body["bootstrap_host"] = "2.2.2.2"
new_extra_request_body["bootstrap_room"] = random.randint(...)
```

其中：

- `bootstrap_host`：正常情况下是 P 服务的地址。
- `bootstrap_room`：正常情况下用于标识一次 KV 传输会话。
- `2.2.2.2`：这里不是实际要连接的地址，而是一个特殊标记，定义在：

```python
FAKE_BOOTSTRAP_HOST = "2.2.2.2"
```

因此，关键点不是 `bootstrap_room=0`，而是 `bootstrap_host` 是否等于 `2.2.2.2`。

## 2. SGLang 如何识别 Fake 请求

在 Prefill 侧，创建 KV sender 时会判断：

```python
backend = (
    TransferBackend.FAKE
    if req.bootstrap_host == FAKE_BOOTSTRAP_HOST
    else self.transfer_backend
)
```

对应代码在 [prefill.py](/sgl-workspace/sglang/python/sglang/srt/disaggregation/prefill.py) 的 `create_sender()`。

Decode 侧也有同样逻辑：

```python
backend = (
    TransferBackend.FAKE
    if _is_fake_transfer(req, self.scheduler.server_args)
    else self.transfer_backend
)
```

对应代码在 [decode.py](/sgl-workspace/sglang/python/sglang/srt/disaggregation/decode.py) 的 `_create_receiver_and_enqueue()`。

所以，即使配置的是 Mooncake、NIXL 或其他真实传输后端，只要请求带有：

```json
{
  "bootstrap_host": "2.2.2.2"
}
```

这个请求就会临时使用 Fake sender/receiver。

## 3. Fake sender 的工作原理

实现位于 [fake/conn.py](/sgl-workspace/sglang/python/sglang/srt/disaggregation/fake/conn.py)。

Fake sender 不创建网络连接，也不访问 `2.2.2.2`：

```python
def init(...):
    pass
```

真正调用 `send()` 时，只做一件事：

```python
self.has_sent = True
```

它的状态变化是：

```text
初始状态
  |
  | poll()
  v
WaitingForInput
  |
  | send() 被调用，设置 has_sent=True
  v
Success
```

也就是说，Prefill 侧仍然会：

1. 计算输入的 KV Cache；
2. 创建 sender；
3. 初始化传输；
4. 执行 send；
5. 轮询传输状态；
6. 等待传输成功；
7. 继续完成请求。

但是第 4 步没有真的把 KV 写入网络，只是把状态标记成“已发送”。

## 4. Fake receiver 的工作原理

Decode 侧使用 Fake receiver，状态逻辑是：

```python
def poll(self):
    if not self.bootstrap_done:
        return KVPoll.Bootstrapping
    if not self.has_sent_metadata:
        return KVPoll.WaitingForInput
    return KVPoll.Success
```

状态变化如下：

```text
初始状态
  |
  | init()
  v
WaitingForInput
  |
  | send_metadata()
  v
Success
```

`init()` 只设置：

```python
self.bootstrap_done = True
```

`send_metadata()` 只设置：

```python
self.has_sent_metadata = True
```

它不会从 Prefill 服务接收真正的 KV 数据。

因此，Decode 侧仍然会经历：

1. 创建 receiver；
2. 执行 bootstrap；
3. 等待 metadata；
4. 发送 KV 页信息；
5. 轮询 receiver 状态；
6. 看到 `Success`；
7. 进入正常 decode 调度。

但所有这些动作都发生在本地内存中，没有真实 P-D 通信。

## 5. 为什么这样就可以只启动 P 或 D 服务

正常 PD 分离流程是：

```text
客户端
  |
  v
Prefill 服务：计算 prompt KV
  |
  | 网络传输 KV
  v
Decode 服务：接收 KV，然后生成 token
```

启用该开关后变成：

```text
客户端
  |
  v
Prefill 或 Decode 服务
  |
  | Fake sender/receiver
  v
本地立即完成“传输”
```

它保留了 PD 分离代码所依赖的控制流程：

- bootstrap；
- sender/receiver 创建；
- metadata 处理；
- transfer polling；
- TP rank 间状态同步；
- 请求进入后续调度。

但删除了最昂贵、也最依赖另一台服务的部分：

- 网络连接；
- P-D 间 KV 拷贝；
- KV 传输带宽；
- 真实传输延迟；
- 两边服务之间的 rendezvous。

因此可以用于：

- 只测试 Prefill 计算性能；
- 只测试 Decode 调度和生成性能；
- 不启动另一侧服务；
- 避免另一侧服务的 QPS、资源和调度干扰。

## 6. 这个开关不能测试什么

这个模式不是“真实 KV 传输的优化模式”，而是测试替身。

它不能反映：

- 实际 KV 传输耗时；
- 网络带宽；
- Mooncake/NIXL 等后端性能；
- P 和 D 之间的通信瓶颈；
- 真实 KV 数据一致性；
- 真实 PD 分离下的端到端输出正确性。

特别是 Fake receiver 的 `send_metadata()` 只记录 metadata，并不接收 KV 内容。因此：

> 使用这个开关得到的 Decode 性能，应该理解为“去除 KV 传输成本后的 Decode 性能”，而不是完整 PD 系统性能。

## 7. `bootstrap_room` 的作用

真实后端中，`bootstrap_room` 通常用于：

- 唯一标识一次传输；
- P、D 两侧匹配同一个请求；
- 关联 metadata 和 KV buffer；
- 支持多请求并发传输。

在 Fake 后端中，它基本不会参与实际通信，只是为了让请求结构和真实 PD 请求保持一致。

所以这两种写法都能触发 Fake 分支：

```json
{
  "bootstrap_host": "2.2.2.2",
  "bootstrap_room": 0
}
```

或者：

```json
{
  "bootstrap_host": "2.2.2.2",
  "bootstrap_room": 3334231
}
```

## 一句话总结

`--enable-test-pd-without-transfer` 的核心原理是：

> 用特殊的 `bootstrap_host=2.2.2.2` 标记请求，在 Prefill 和 Decode 两侧将真实 KV 传输类替换成 Fake sender/receiver；Fake 类只推进状态机，不进行网络通信和 KV 拷贝，因此保留 PD 请求流程，却可以单独测 P 或 D 服务。

## 为什么还要设置 `bootstrap_room`

因为请求处理代码本来要求 PD 请求携带这些字段：

```text
bootstrap_host
bootstrap_room
```

为了让 Fake 请求也能走和真实 PD 请求相同的代码路径，Benchmark 仍然填入这两个字段。

但在 Fake 后端里，`bootstrap_room` 不再用于真正建立连接或查找传输房间。

例如：

```python
FakeKVSender(
    bootstrap_addr="2.2.2.2:port",
    bootstrap_room=123,
)
```

虽然构造函数接收了这些参数，但 Fake sender 不会使用它们建立网络连接。

## 实际执行过程

假设只启动了 Prefill 服务，并发送：

```json
{
  "input_ids": [[1, 2, 3]],
  "bootstrap_host": "2.2.2.2",
  "bootstrap_room": 123
}
```

Prefill 侧执行：

```text
1. 收到请求
2. 发现 bootstrap_host == "2.2.2.2"
3. 创建 FakeKVSender
4. 计算 prompt 的 KV Cache
5. 调用 FakeKVSender.send()
6. Fake sender 只把 has_sent 设置为 true
7. 下一次 poll() 返回 Success
8. 请求继续完成
```

它不会真的把 KV 发到 `2.2.2.2`。

如果只启动 Decode 服务，则 Decode 侧会：

```text
1. 收到请求
2. 发现 bootstrap_host == "2.2.2.2"
3. 创建 FakeKVReceiver
4. init()，表示 bootstrap 完成
5. send_metadata()，表示 metadata 已到达
6. poll() 返回 Success
7. Decode 继续执行
```

它也不会真的从 Prefill 服务接收 KV。

因此，整个判断实际上只有这一句：

```python
req.bootstrap_host == "2.2.2.2"
```

它的作用等价于：

```python
if request.is_test_without_transfer:
    use_fake_kv_transfer()
```

只是当前实现没有额外增加 `is_test_without_transfer` 字段，而是借用了 `bootstrap_host` 来表达这个意思。

最后强调一下：

```text
bootstrap_host = "2.2.2.2"
```

不是：

```text
连接 2.2.2.2
```

而是：

```text
不要连接任何 Prefill 服务，使用 Fake KV 传输逻辑
```

`bootstrap_room` 只是为了让请求格式仍然符合 PD 请求格式；真正触发 Fake 模式的是 `bootstrap_host` 的特殊值。

- D 节点知道序列长度是 8K；
- D 节点已经分配了 8K KV 空间；
- Attention kernel 可以读取这些地址；
- Scheduler 可以正常执行逐 token decode；
- CUDA kernel、显存访问和调度流程仍然会运行。

普通 Full Attention 中，生成新 token 时需要看到此前所有 token：

```text
token 10000
  -> Attention 读取 token 1～9999 的 KV
```

所以完整历史 KV 要一直保留。

```text
token 10000
  -> 只读取最近 window 范围内的 KV
```

因此 SWA pool 主要存储：

```text
每个请求最近一个滑动窗口内、未压缩的 K/V Cache
```

对于 DSV4，整体结构可以粗略理解为：

```text
最近的 token
  -> SWA pool，保存较完整的近期 KV

较早的历史 token
  -> C4/C128 pool，保存压缩后的历史信息
```

也就是：

| Pool | 保存内容 |
|---|---|
| `swa` | 最近滑动窗口内的未压缩 KV |
| `c4` | 按 4 倍比例压缩的历史 KV/索引 |
| `c128` | 按 128 倍比例压缩的更早历史信息 |
| `c4_state` | C4 压缩过程需要的状态 |
| `c128_state` | C128 压缩过程需要的状态 |

随着 Decode 继续进行，SWA 大致按下面的方式工作：

```text
旧窗口：
[token 1 ... token 128]

生成新 token 后：
[token 2 ... token 129]
```

最老的 token 离开窗口，其 SWA 槽位可以被回收；新的 token 写入 SWA pool。

因此 SWA 不一定随序列长度无限增长。稳态下，每个请求主要保留最近一个窗口，但在 chunked prefill、页对齐和调度重叠时还需要额外临时空间。

- speculative decoding 的额外 token；
- 已缓存但可驱逐的 SWA token；
- C4/C128 pool 是否先用满；
- `max_running_requests`。

所以不能仅用 `153344 / 输入长度` 计算并发。

## 会受到显存利用率影响吗

要区分“容量”和“使用率”。

### 容量受启动显存预算影响

`153344` 是服务启动时计算出来的固定容量，会受到这些参数影响：

```text
--mem-fraction-static
模型权重大小
DSpark draft 权重
CUDA Graph 占用
其他固定状态内存
swa_full_tokens_ratio
```

基本过程是：

```text
GPU 总显存
- Target 权重
- Draft 权重
- CUDA Graph
- 固定状态
= 可用于 KV pool 的显存
```

再按照 `swa_full_tokens_ratio=0.1` 分配 SWA 的逻辑容量。

如果提高：

```text
--mem-fraction-static
```

通常可以给 KV pool 更多显存，`full` 和 `swa` 都可能增加；但设置过高可能导致运行时临时张量没有空间，从而 OOM。

如果把：

```text
swa_full_tokens_ratio=0.1
```

调整为：

```text
swa_full_tokens_ratio=0.2
```

理论上 SWA 容量相对于 full 会增大，但每个 full-token 的综合显存成本也会增加，最终计算得到的 `full_token` 可能下降。它不是无成本扩容。

### 运行中的显存利用率不会动态改变容量

服务启动后：

```text
swa=153344
```

一般就是固定的逻辑容量，不会因为当前 GPU 显存利用率是 30% 或 90% 就自动扩大或缩小。

运行日志中的：

```text
swa token usage: 0.03
```

表示：

```text
当前已使用 SWA token / SWA 总容量
```

例如：

```text
0.03 × 153344 ≈ 4600 个 SWA token 槽位
```

这是 SWA pool 的占用率，不是 `nvidia-smi` 看到的显存带宽利用率。

## 它会不会限制最大并发

会，但当前配置大概率先受到 `max_running_requests` 限制。

单个 DP rank 的并发上限可以粗略表示为：

```text
min(
  max_running_requests,
  full pool 能支持的请求数,
  swa pool 能支持的请求数,
  c4 pool 能支持的请求数,
  c128 pool 能支持的请求数
)
```

你当前每个 DP rank：

```text
max_running_requests=2
swa=153344
```

只有两个运行请求时，SWA pool 通常不会先成为瓶颈。因此当前实际全局运行并发仍然是：

```text
2 请求/DP × 8 DP = 16
```

一句话总结：

> `swa=153344` 是每个 DP rank 为所有请求共享预留的“近期滑动窗口 KV Cache”容量；它在启动时受显存预算和 `swa_full_tokens_ratio` 影响，运行中容量基本固定，日志中的 `swa token usage` 才表示当前用了多少。
