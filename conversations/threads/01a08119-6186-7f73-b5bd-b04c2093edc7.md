先给结论：参考仓库中的 GLM-5.2 实现，CP 切的是 token/序列维度，不是 MLA 的 head 或 latent 维度。GLM-5.2 实际走的是 DSA CP 分支；DSA 底层仍使用 MLA 的压缩 KV 表示。MoE 是否保持 CP 分片，取决于 MoE 的 A2A/EP 配置。

### 1. GLM-5.2 里 CP 怎么切

测试配置是：

```bash
--tp 4
--attn-cp-size 4
--enable-prefill-cp
--cp-strategy interleave
--dsa-prefill-backend trtllm
```

见 [GLM-5.2 CP 测试](/sgl-workspace/sglang-official-pr36185/test/registered/models_e2e/test_dsa_glm52_pd_mtp_cp_layersplit.py:37)。

在 `CP=4` 的 interleave 策略下：

```text
CP0: token 0, 4,  8, 12, ...
CP1: token 1, 5,  9, 13, ...
CP2: token 2, 6, 10, 14, ...
CP3: token 3, 7, 11, 15, ...
```

实现见 [interleave.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/cp/interleave.py:15)。

CP-v2 的完整生命周期是：

```text
完整 embedding / positions
          │
          ├── 按 token_idx % CP 切给各 CP rank
          │
          ▼
各 rank 跑自己的 token slice
          │
          ▼
最后 all-gather + 恢复自然 token 顺序
          │
          ▼
logits
```

切分和最终 gather 在 [eager_runner.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/model_executor/runner/eager_runner.py:380)。

对于 `TP=4, DP=1, CP=4`：

```text
attn_cp_size = 4
attn_tp_size = TP / (DP × CP) = 1
```

也就是 4 张卡主要沿序列切，attention 不再沿 head 做 TP=4。

### 2. MLA 在 CP 下怎么处理

这里不是把 MLA latent dimension 切成四份，而是：

- Q：只计算当前 CP rank 所拥有的 token。
- 压缩 KV：先由各 rank 为自己的 token 生成。
- Attention 前：把各 rank 的 MLA latent KV all-gather 回完整上下文。
- Attention 输出：仍然只产生当前 rank 的 local Q token 输出。

原因很直接：虽然 Q 可以按 token 切，但每个 Q 都可能需要看到其他 rank 上的历史 KV；只保留 local KV 会破坏 attention 语义。

代码 gather 的不是展开后的完整多头 K/V，而是：

```text
[k_nope latent | k_rope]
```

然后恢复成完整 token 顺序，见 [materialize_full_mla_kv](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/cp/interleave.py:258)。这也是 MLA 很适合做 CP 的地方：通信的是压缩 latent KV，通常比完整 MHA KV 小得多。

要特别注意：GLM-5.2 配置包含 `index_topk`，因此被识别成 DSA 模型。代码会设置：

```text
dsa_enable_prefill_cp = true
mla_enable_prefill_cp = false
```

见 [deepseek_v2.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/models/deepseek_v2.py:2642)。所以它在开关意义上是“DSA CP”，不是普通 DeepSeek-V3 的“MLA CP”，但 DSA attention 内部仍复用了 MLA latent KV 和 absorbed attention。

### 3. MoE 会切吗

分两种情况。

#### GLM-5.2 interleave + 默认无 A2A

这种配置下，模型主干的 hidden state 是 CP-local 的，但进入 MoE 前会临时 all-gather 成完整 token 集：

```text
CP-local hidden
      │
      ├── all-gather
      ▼
完整 token hidden
      │
      ▼
TP MoE / router / experts
      │
      ├── reduce/scatter
      ▼
回到 CP-local hidden
```

所以严格来说：

- 模型层间 token 是切着的；
- 但 MoE 算子本身没有真正享受到 CP-local token 计算；
- 每个 MoE 层前后会有额外通信。

代码明确写了：DSA CP 和 MLA CP 当前还不支持 `MOE_FULL`，无 A2A 时回退到 `FULL`，见 [communicator.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/communicator.py:389)。

#### 使用 DeepEP/其他 MoE A2A

如果启用 MoE A2A/EP：

```text
CP-local tokens
      │
      ├── router
      ├── A2A dispatch 到 expert owner
      ▼
各 rank 的本地 experts
      │
      ├── A2A combine
      ▼
原 CP-local token
```

这时 MoE 可以保持 `SCATTERED`，不需要先复制完整 token。CP 切 token，EP 切专家，A2A 负责两种布局之间的数据搬运。

仓库里的 zigzag DSA CP 会自动要求：

```text
moe_a2a_backend = deepep
ep_size = tp_size
moe_dense_tp_size = 1
batch_size = 1
```

见 [DeepSeek/GLM CP 配置覆盖](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/arg_groups/model_overrides/deepseek_v2.py:42)。

因此，“MoE 会不会切”的准确回答是：

- CP 本身不切 expert 权重，只切 token。
- Expert 权重由 TP/EP 配置决定。
- 无 A2A：GLM-5.2 当前实现会在 MoE 前 gather，MoE 不保持 CP token 分片。
- 有 DeepEP/A2A：token 保持分片，通过 dispatch/combine 路由到切分后的 experts。

### 4. 这套设计解决什么问题

基础 CP 解决的是长 prompt prefill：

- 单卡 attention 计算量过大；
- 单卡临时张量和 KV/indexer cache 压力大；
- TP 已经不能有效继续切 attention，或者 TP 通信/小矩阵效率变差；
- 希望多卡同时处理同一个长序列。

但真正难点不是“把 token 除以卡数”，而是处理三个布局冲突：

1. Attention 需要 local Q + global KV。
2. MoE 希望按 expert 路由，而 CP 是按 token 排列。
3. Residual、LayerNorm、KV 写入和最终 logits 必须恢复一致的 token 顺序。

GLM-5.2 还暴露了另一个问题：即使 token 已按 CP 切开，为了 DSA/MLA attention，各 rank 仍可能物化完整的 KV/indexer cache，导致显存并没有按 CP 倍数下降。

因此测试又加了：

```bash
--enable-dsa-cache-layer-split
```

它按“层”把 KV/indexer cache 分给不同 CP rank：

```text
CP0 owns layers [0 ... a)
CP1 owns layers [a ... b)
CP2 owns layers [b ... c)
CP3 owns layers [c ... L)
```

访问非本 rank 所属层时，由 owner broadcast 到一个小的 scratch buffer。每张卡只需要大约：

```text
ceil(num_layers / CP) + 1 个 layer cache
```

实现说明见 [cp/utils.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/cp/utils.py:56)。

这个 layer split 目前只适合 PD 分离：

- Prefill worker：按层分摊缓存。
- Decode worker：接收完整的 cache shard，正常 decode。
- Unified server 不适合，因为 decode 时非 owner rank 没有完整层缓存。

所以 GLM-5.2 这里最终要解决的核心是：在不改变模型结果的前提下，让长上下文 prefill 的 attention 计算、KV/indexer 显存和 MoE 通信都能随多卡扩展。目前 attention 和 cache 已经能切，但“无 A2A 的 MoE 保持 CP-local”仍是明显的优化缺口。

### CP 能提高并发吗？

普通 prefill CP 更准确地说是提高“单个长请求的并行度”，不直接提高并发。

例如原来 4 张 GPU 可以分别服务 4 个请求；设置 `CP=4` 后，4 张卡共同处理一个请求：

```text
无 CP：4 GPU × 1 request/GPU ≈ 4 个并发执行单元
CP=4：4 GPU × 同一个 request ≈ 1 个并发执行单元
```

它可能缩短长 prompt 的 TTFT，从而让请求更快离开 prefill 阶段，间接改善高负载吞吐；但它占用更多 GPU，并带来 KV all-gather、MoE dispatch 等通信，所以不保证总体并发提高。

CP 最适合：

- 单请求 prompt 很长；
- 单卡 prefill 太慢或放不下；
- 目标是降低长请求 TTFT；
- 并发不高，或使用独立 prefill 集群。

若目标是大量短请求并发，DP 通常比 CP 更直接。实践上可以使用 `DP × CP`：DP 提供多请求副本，CP 加速每个副本里的长请求。

### CP 能节省 KV cache 吗？

关键要区分每卡显存和集群总显存。

#### 普通 prefill CP

输入 token 虽然被切成 `1/CP`，但每个 local Q 仍要访问完整上下文的 KV。因此实现往往会：

1. 每个 rank 生成 local token 的压缩 KV；
2. attention 前 all-gather；
3. 各 rank 获得完整 KV；
4. 分别计算 local Q。

所以普通 CP 可以减少部分激活和 Q 计算，但 KV cache 若最终在每卡复制，不能按 `1/CP` 节省；还会产生 KV all-gather 通信和临时 buffer。

GLM-5.2 的 interleave 路径就会 gather MLA latent KV，见 [interleave.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/cp/interleave.py:258)。

#### 真正 KV-sharded 的 CP/DCP

如果 KV cache 按 token/上下文分布存储，每个 rank 只保留大约：

```text
单卡 KV ≈ 完整 KV / CP
```

attention 在各 rank 上对 local KV 算 partial result，再通过通信合并 output 和 LSE。这能显著降低每卡 KV 显存，从而容纳更长上下文或更大 batch。

但总 KV 数据仍然大约不变：

```text
集群总 KV ≈ 原始完整 KV
```

节省的是每卡容量，不是模型所需的总信息量，并且代价是 decode 每层通信。

#### GLM-5.2 的特殊优化

GLM-5.2 的：

```bash
--enable-dsa-cache-layer-split
```

会让不同 CP rank 只长期保存一部分 DSA KV/indexer 层。每卡大约保存：

```text
ceil(num_layers / CP) + 1 个 layer cache
```

因此它确实降低了 prefill worker 的每卡 KV/indexer 显存，接近按 CP 分摊；但非 owner 层需要 broadcast，并且当前设计主要用于 PD 分离，decode worker仍接收正常的完整 cache shard。参考 [cp/utils.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/cp/utils.py:87)。

一句话总结：

> CP 的首要收益是并行处理一个长上下文、降低 TTFT；提高并发只是潜在的间接收益。只有 KV 真正分片存储的 DCP 或 GLM-5.2 DSA cache layer split，才能明显降低每卡 KV cache 开销；普通 prefill CP 不一定能做到。

如果你说的是这台机器上的 GLM-5.2：8 张 RTX PRO 5000 72GB，那么 decode 节点应开的是 DCP（`--dcp-size`），不是 prefill CP（`--enable-prefill-cp`）。

最重要的一点是：

> “decode 只开 CP”并不等于不用 TP。GLM-5.2 权重仍然要靠 TP/EP 分布到多张卡；DCP 只是额外把 KV cache 沿上下文切开。

例如：

```bash
--tp-size 8
--dcp-size 4
```

表示模型依然是 TP8，但每 4 个连续 rank 构成一个 DCP group：

```text
DCP group 0: GPU 0,1,2,3
DCP group 1: GPU 4,5,6,7
```

这刚好契合本机两个 NUMA 域；比 `DCP=8` 更合理。

### Decode 时具体怎么跑

假设一个请求已有 128K KV，`DCP=4`：

```text
GPU0 保存位置 0,4,8,...      约 32K
GPU1 保存位置 1,5,9,...      约 32K
GPU2 保存位置 2,6,10,...     约 32K
GPU3 保存位置 3,7,11,...     约 32K
```

每生成一个 token时：

```text
当前 Q
 ├─ GPU0 对自己的 1/4 KV 算 partial attention
 ├─ GPU1 对自己的 1/4 KV 算 partial attention
 ├─ GPU2 对自己的 1/4 KV 算 partial attention
 └─ GPU3 对自己的 1/4 KV 算 partial attention
          │
          ▼
合并各 rank 的 output + LSE
          │
          ▼
得到和完整 attention 等价的结果
```

仓库采用的位置归属规则就是：

```text
position % dcp_size == dcp_rank
```

见 [layout.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/layers/dcp/layout.py:25)。

### KV 容量能增加多少

理论上：

| 配置 | 每卡保存单请求 KV | 集群逻辑 KV 容量 |
|---|---:|---:|
| DCP1 | 完整 KV | 1× |
| DCP2 | 约 1/2 | 约 2× |
| DCP4 | 约 1/4 | 约 4× |
| DCP8 | 约 1/8 | 约 8× |

因此，如果当前 decode 并发受 KV 显存限制，DCP4 确实可能让可容纳的并发 token 接近原来的 4 倍。例如原先能容纳 16 个平均 64K 上下文，理论容量可能接近 64 个；实际还要扣除页对齐、CUDA Graph、请求元数据和临时通信 buffer。

注意这不是节省整个集群的 KV 总量，而是把 KV 分摊到不同 GPU，提升逻辑容量。

### 会不会提高 decode 吞吐

不一定，更可能是“容量提高，单步延迟变差”。

GLM-5.2 使用 DSA，原本 decode attention 已经通过 indexer 只选择少量 KV。DCP 后每层还要合并 partial attention 和 LSE，因此：

- 长上下文、KV 显存不足：DCP 很有价值；
- 高并发且 KV 已经顶满：可能提升可服务并发；
- 短上下文或低并发：通信开销可能超过 attention 计算收益；
- 不会让 MoE 变成 CP：MoE/专家权重仍按原来的 TP/EP 路径运行。

尤其这台机器没有 NVLink：

```text
GPU 0–3：同一 NUMA 域，NODE
GPU 4–7：同一 NUMA 域，NODE
两个 NUMA 域之间：SYS
```

所以：

- `DCP=4`：DCP 通信留在各 NUMA 半区，优先测试；
- `DCP=8`：每层通信跨 NUMA/CPU interconnect，延迟风险很高；
- `fi_a2a` 不适合这里，它面向 GB200 NVL72 一类 MNNVL fabric；
- 可以比较默认 `ag_rs` 和普通 `a2a`，但 PCIe 机器上必须实测。

### 推荐配置

如果 GLM-5.2 decode 当前必须 TP8 才能放下，第一组实验建议：

```bash
--tp-size 8
--dcp-size 4
--dcp-comm-backend ag_rs
--kv-cache-dtype fp8_e4m3
```

然后对照：

```text
A: TP8 + DCP1
B: TP8 + DCP4 + ag_rs
C: TP8 + DCP4 + a2a
D: TP8 + DCP8（只作为容量/性能上限实验）
```

重点测：

- `max_total_num_tokens`：DCP4 应接近 DCP1 的 4 倍；
- decode tokens/s；
- inter-token latency；
- 不同上下文长度下的最大稳定并发；
- NCCL 通信时间占比。

如果是 PD 分离的纯 decode worker，当前代码还有约束：

- transfer backend 要使用 Mooncake 或 NIXL；
- decode DCP 当前要求 chunk cache；
- 不支持 decode radix cache；
- 不支持 HiCache。

所以概括下来：

> 在这台 8×72GB PCIe 机器上，GLM-5.2 decode 开 DCP4 的主要收益是把 KV 分到 GPU 0–3、4–7 两组内，使逻辑 KV 容量和“受 KV 限制的并发”接近提升 4 倍；它大概率不会直接提高每 token 的计算吞吐。DCP8 容量更大，但跨 NUMA 通信代价明显，通常不是第一选择。

# 3. Attention 部分：MLA 是什么

先看普通 Attention。

普通多头注意力会为每个 token 生成：

```text
Q：当前 token 想找什么
K：当前 token 能被什么查询匹配
V：当前 token 携带的内容
```

然后计算：

```text
Attention(Q,K,V) = softmax(QKᵀ) V
```

问题是，decode 时每生成一个 token，都要保留此前所有 token 的 K 和 V，这就是 KV cache。

如果：

```text
上下文长度 = 128K
层数       = 78
heads      = 64
```

普通多头 K/V 会非常大。

## MLA 的办法

MLA 是 Multi-head Latent Attention。核心思想是：

> 不直接缓存每个 head 展开后的完整 K/V，而是缓存一个低维压缩表示。

GLM-5.2 中，每个 token 的 hidden state 是 6144 维。它生成两条低秩路径：

```text
hidden state：6144
      │
      ├── Q 压缩到 q_latent：2048
      │       │
      │       └── 展开成 64 个 query heads
      │
      └── KV 压缩到 kv_latent：512
              +
          RoPE 部分：64
```

Q 的每个 head 是：

```text
192 维内容部分（NoPE）
+
64 维位置部分（RoPE）
=
256 维
```

KV cache 主要保存：

```text
512 维 KV latent
+
64 维 RoPE key
=
每层、每 token 约 576 个元素
```

而不是缓存：

```text
64 heads × 完整 K/V
```

可以简单理解成：

```text
普通 Attention：

token ──> K1 K2 K3 ... K64
      └─> V1 V2 V3 ... V64
           全部存进 KV cache


MLA：

token ──> 一个 512 维压缩包 + 64 维位置信息
           存进 KV cache
```

因此 MLA 的主要作用是：

> 大幅降低长上下文的 KV cache 大小和显存带宽。

“吸收式 MLA”还会把部分投影矩阵的运算顺序重新组合，让 attention 可以直接使用压缩 latent，避免每次把完整 K/V 全部展开出来。

# 4. DSA 又是什么

只有 MLA，虽然 KV cache 小了，但 attention 仍可能需要扫描所有历史 token。

例如上下文有 128K token：

```text
新 token 的 Q
    ×
128K 个历史 KV
```

每一层都扫描 128K，decode 仍然很昂贵。

GLM-5.2 又增加了 DSA，可以把它理解为：

> 先用一个便宜的检索器，从全部历史 token 中找出最相关的 2048 个，再做真正的 MLA attention。

流程是：

```text
当前 query
    │
    ▼
轻量 Indexer
    │
    ├── 给历史 token 打分
    │
    ▼
选出 Top 2048 个位置
    │
    ▼
只对这 2048 个 KV 做 MLA Attention
```

原本可能是：

```text
Q × 128K KV
```

现在接近：

```text
Indexer 扫描/检索
+
Q × Top-2048 KV
```

所以：

- MLA 主要解决 KV cache 太大；
- DSA 主要解决长上下文 attention 计算太多；
- 两者解决的是不同问题。

GLM-5.2 的 `index_topk=2048`，也就是 DSA attention 最终选取 2048 个相关 KV 位置。

## 为什么有些层共用索引

GLM-5.2 并非每一层都重新计算一次 Top-2048。

配置大致呈现：

```text
某一层：重新运行 indexer，计算 Top-2048
后面几层：复用前面算出的 Top-2048
再下一组：重新计算
```

可以理解为：

```text
Layer 6：重新搜索相关 token
Layer 7：复用 Layer 6 的搜索结果
Layer 8：复用 Layer 6 的搜索结果
Layer 9：复用 Layer 6 的搜索结果
Layer 10：重新搜索
```

这样可以进一步减少 indexer 的开销。

# 5. MoE 部分是什么

普通 Transformer 的 FFN 是：

```text
每个 token
   │
   ▼
同一个大 FFN
```

GLM-5.2 使用 MoE，即 Mixture of Experts：

```text
              ┌── Expert 0
              ├── Expert 1
token → Router├── Expert 2
              ├── ...
              └── Expert 255
```

模型一共有 256 个 routed experts，但一个 token 不会经过全部 256 个。

Router 会为当前 token 选择 Top-8：

```text
一个 token
   │
   ▼
Router 对 256 个专家打分
   │
   ▼
选中 8 个 routed experts
   │
   ├── Expert 7
   ├── Expert 19
   ├── Expert 43
   ├── Expert 81
   ├── Expert 102
   ├── Expert 145
   ├── Expert 201
   └── Expert 250
```

然后把这 8 个专家的结果加权合并：

```text
MoE(x) = w₁E₁(x) + w₂E₂(x) + ... + w₈E₈(x)
```

除此之外还有 1 个 shared expert：

```text
最终 FFN 结果
=
Top-8 routed experts 的结果
+
shared expert 的结果
```

共享专家可以学习所有 token 都经常需要的通用能力；路由专家则可以分别学习代码、数学、语言、知识等不同模式。

## MoE 为什么能把模型做得很大

虽然共有 256 个专家，但每个 token 只激活 8 个：

```text
总参数：包含 256 个专家
每 token 计算：主要只计算其中 8 个
```

所以 MoE 的价值是：

> 增加模型总容量，但不让每个 token 的计算量与总参数量等比例增长。

不过，所有专家权重仍然要放到 GPU 集群里。因此 GLM-5.2 需要多卡，主要不是因为每个 token 会计算全部权重，而是因为所有专家参数必须被保存。

# 7. Prefill 和 Decode 的区别

模型结构相同，但运行方式不同。

## Prefill

输入一整段 prompt：

```text
“请帮我分析这段 100K 的代码……”
```

100K 个 token 可以一次送入模型：

```text
100K tokens
    │
    ▼
78 层批量计算
    │
    ▼
为所有 token 建立 KV cache
```

特点：

- token 数很多；
- GEMM 很大；
- attention 计算重；
- 适合并行；
- 最终产生大量 KV cache。

## Decode

之后一次只生成一个或几个 token：

```text
第一个输出 token
第二个输出 token
第三个输出 token
...
```

每一步都是：

```text
1 个新 token
    │
    ├── 经过 78 层
    ├── 查询已有 KV cache
    ├── 追加自己的 KV
    ▼
预测下一个 token
```

特点：

- 每步的新 token 很少；
- 必须反复读取历史 KV；
- 对显存带宽和通信延迟敏感；
- MoE 每一步都要进行路由。

对，GLM-5.2 的 decode 主路径基本是 absorbed MLA。需要纠正一个容易混淆的点：

> `192+64=256` 是 Q 在吸收前的 head 形状；KV cache 保存的是 `512+64`。Q 不进 KV cache。

DSA 则是在 absorbed MLA 前面增加了一套“检索索引”。

## 1. 不带 DSA 的 absorbed MLA

对历史 token `j`，模型先得到：

```text
c_j^KV：512 维 KV latent
k_j^R ：64 维 RoPE key
```

长期保存的是：

```text
KVCache[j] = [c_j^KV(512), k_j^R(64)]
```

当前 query token `i` 得到：

```text
q_i^C：每个 head 192 维内容 query
q_i^R：每个 head 64 维 RoPE query
```

### 未吸收的算法

未吸收时，需要把 512 维 latent 展开成每个 head 的完整 K/V：

```text
c_j^KV(512)
    │
    ├── W_K ──> K_j^C：64 heads × 192
    │
    └── W_V ──> V_j  ：64 heads × 256
```

然后计算：

```text
score(i,j)
=
q_i^C · K_j^C
+
q_i^R · k_j^R
```

问题是，如果有 128K 历史 token，把它们全部展开成 64 头 K/V，临时内存和计算会很大。

## 2. Absorb 到底吸收了什么

原来的内容 attention 是：

```text
q_i^C · (c_j^KV W_K)
```

利用矩阵乘法结合律，可以改写成：

```text
(q_i^C W_Kᵀ) · c_j^KV
```

也就是不再把每个历史 KV 展开，而是先把当前 Q 从 192 维映射到 512 维：

```text
q_i^C：192
   │
   └── 吸收 W_K
          │
          ▼
q_i^abs：512
```

于是实际 attention 变成：

```text
Query：
[q_i^abs(512), q_i^R(64)]

Key：
[c_j^KV(512), k_j^R(64)]

Value：
c_j^KV(512)
```

因此 absorbed MLA 核心计算近似是：

```text
score(i,j)
=
q_i^abs · c_j^KV
+
q_i^R · k_j^R
```

attention 输出先是每个 head 的 512 维 latent：

```text
o_i^latent：512
```

再通过吸收后的 V 投影恢复：

```text
o_i^latent(512)
      │
      └── W_V
             │
             ▼
        head output(256)
```

所以，“吸收”不是换了一种 KV cache，而是改变计算顺序：

```text
未吸收：
历史 latent → 展开完整 K/V → attention

吸收：
当前 Q → 变换到 latent 空间 → 直接和历史 latent attention
```

## 3. DSA 怎么接进来

DSA 不参与上述 MLA 代数变换。它在真正 attention 之前负责挑选历史位置：

```text
                    当前 token
                       │
              ┌────────┴────────┐
              │                 │
         DSA Indexer        MLA Query
         检索路径           正式计算路径
              │                 │
      从所有历史位置中           │
       选 Top-2048              │
              │                 │
              └──── indices ────┘
                       │
                       ▼
       absorbed MLA 只读取这些位置的
          [cKV(512), kRoPE(64)]
```

所以完整流程是：

```text
1. DSA 使用自己的小型 index K cache 扫描历史
2. 返回 Top-2048 token 位置
3. 根据位置读取主 MLA KV cache
4. absorbed MLA 对这 2048 个位置进行正式 attention
```

比如历史长度是 128K：

```text
主 MLA KV cache：仍然保存全部 128K token
DSA index cache：也覆盖全部 128K token
TopK indices：本次 query 只选 2048 个位置
正式 MLA：只算这 2048 个位置
```

DSA 减少的是正式 attention 读取/计算的数量，并不会只保存 2048 个 KV。否则下一个 query 想选择不同位置时，数据已经丢了。

## 4. 为什么有两套 cache

GLM-5.2 decode 实际有：

```text
A. 主 MLA KV cache
   用于最终精确 attention

B. DSA index K cache
   用于便宜地搜索候选位置
```

### 主 MLA cache

逻辑内容：

```text
cKV latent：512
RoPE key  ：64
```

即每层、每历史 token 为 576 个逻辑元素。

### DSA index cache

Indexer 配置是：

```text
index query heads：32
index head dim   ：128
```

但历史侧使用的是一份共享的 index K，而不是缓存 32 份：

```text
每个历史 token：
128 维 index K，FP8
+
4 字节 scale
=
约 132 字节
```

当前 query 的 32 个 index heads 是临时计算的，不长期缓存。它们与历史的 128 维 index K 打分，得到 Top-2048。

很多层还会复用前一层的 TopK 结果，所以这些层不会单独分配 index K cache。代码里复用 TopK 的层直接使用零行占位，见 [index_key_cache.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/mem_cache/index_key_cache.py:40)。

## 5. 实际存储字节数

前面说的“576 个元素”是逻辑结构，不等于一定占 576 字节。

### BF16 KV cache

如果两部分都按 BF16：

```text
(512 + 64) × 2 bytes
= 1152 bytes / token / layer
```

### FP8 + TRTLLM DSA backend

当前代码中，TRTLLM 保持 raw MLA layout：

```text
512 FP8 latent
+
64 FP8 RoPE
=
576 bytes / token / layer
```

配置计算见 [kv_cache_configurator.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/mem_cache/kv_cache_configurator.py:2215)。

### FP8 + SGLang scaled layout

某些非 TRTLLM CUDA 后端采用：

```text
512 bytes  latent FP8
16 bytes   latent scales
128 bytes  64 个 BF16 RoPE
--------------------------------
656 bytes / token / layer
```

具体布局见 [memory_pool.py](/sgl-workspace/sglang-official-pr36185/python/sglang/srt/mem_cache/memory_pool.py:4216)。

再加上有独立 indexer 的层：

```text
约 132 bytes / token / indexer layer
```

所以 DSA 相比纯 MLA 确实多了一份 index cache，但它换来的是把正式 attention 从最长约百万 KV 缩减为 Top-2048。

## 6. Absorb 前后存储有没有区别

长期 KV cache 基本没有区别：

| 路径 | 长期保存 |
|---|---|
| 未吸收 MLA | `cKV(512) + kRoPE(64)` |
| absorbed MLA | `cKV(512) + kRoPE(64)` |
| DSA + absorbed MLA | 主 MLA cache，再加 index K cache |

真正不同的是运行时临时张量：

```text
未吸收 MLA：
可能临时展开
K = [tokens, heads, 192]
V = [tokens, heads, 256]

absorbed MLA：
不展开历史完整 K/V
直接使用
K/V latent = [tokens, 512]
```

因此 absorbed MLA 主要减少的是：

- 历史 K/V 展开计算；
- 临时张量；
- 显存带宽；
- decode attention 的数据读取量。

DSA 再进一步减少“正式 MLA 实际访问多少个历史 token”。

一句话总结：

> GLM-5.2 保存完整历史的压缩 MLA cache；DSA 额外保存一份很小的检索 index cache，先找出 Top-2048 位置；absorbed MLA 再直接使用这些位置的 512+64 压缩 KV 完成正式 attention。Absorb 改变的是计算顺序，不是主 KV cache 的逻辑内容。

## 先看保存了什么

对每个历史 token，GLM-5.2 只保存：

```text
C：512维压缩内容
R：64维位置向量
```

```text
历史 token 的 KV cache = [C(512), R(64)]
```

## 不吸收：先展开历史 KV

一个历史 token 的压缩内容是：

```text
C：512维
```

用两个矩阵把它展开为该 head 的 K 和 V：

```text
C(512) × Wk(512×192) → K(192)
C(512) × Wv(512×256) → V(256)
```

当前 token 的 Q 内容部分是：

```text
Q(192)
```

然后做普通 attention：

```text
分数 = Q(192) · K(192)
输出 = attention权重 × V(256)
```

完整过程：

```text
历史 C(512)
   ├── Wk → 历史 K(192) ──┐
   │                       ├── Q·K → attention权重
   └── Wv → 历史 V(256) ──┘            │
                                       ▼
                               加权求和 V(256)
```

如果有 100K 个历史 token，就要展开：

```text
100K × K(192)
100K × V(256)
```

历史序列越长，这个展开越贵。

## 吸收：不展开历史 KV

原来的内容分数是：

```text
Q · K
```

而：

```text
K = C × Wk
```

代入得到：

```text
Q · (C × Wk)
```

改变乘法顺序：

```text
(Q × Wkᵀ) · C
```

因此可以先把当前 Q 从 192 维变成512维：

```text
Q(192) × Wkᵀ(192×512)
          ↓
     Q_abs(512)
```

然后直接与历史压缩向量 `C(512)` 点积：

```text
分数 = Q_abs(512) · C(512)
```

完整过程变成：

```text
当前 Q(192)
    │
    └── Wkᵀ → Q_abs(512)
                    │
                    ├── 与所有历史 C(512) 点积
                    │
                    ▼
               attention权重
                    │
                    ├── 对历史 C(512) 加权求和
                    ▼
             latent输出(512)
                    │
                    └── Wv → 最终输出(256)
```

这就是“吸收”。

所谓吸收，就是：

```text
原来：
对每个历史 token 执行 C × Wk、C × Wv

改成：
把 Wk 移到当前 Q 一侧
把 Wv 移到 attention 求和之后
```

于是历史 `C` 不需要展开。

## 两种方式对比

### 不吸收

```text
历史 C
  │
  ├── 展开成 K
  └── 展开成 V
          │
当前 Q ── Attention ──> 输出
```

### 吸收

```text
当前 Q ──变成 Q_abs──┐
                     ├──直接读取历史 C
历史 C ──────────────┘
                     │
                latent输出
                     │
                    Wv
                     │
                  最终输出
```

两者数学结果相同，执行顺序不同。

| 项目 | 不吸收 | 吸收 |
|---|---|---|
| 主 KV cache | `C(512)+R(64)` | `C(512)+R(64)` |
| 是否展开历史 K | 是 | 否 |
| 是否展开历史 V | 是 | 否 |
| Q 内容维度 | 192 | 转换成512 |
| attention 输出 | 256维 V 空间 | 先在512维 latent 空间求和 |
| 最后是否乘 Wv | V 已提前展开 | 求和后再乘 |

所以，吸收与不吸收没有两种不同的长期 KV 存储格式。

## 64 维 RoPE 放在哪里

前面只讲了 192 维内容部分。完整分数还有 64 维位置部分：

```text
内容分数：
Q_abs(512) · C(512)

位置分数：
Q_rope(64) · K_rope(64)

总分数：
内容分数 + 位置分数
```

因此 absorbed MLA 实际送进 attention 的形式是：

```text
Query = [Q_abs(512), Q_rope(64)]
Key   = [C(512),     K_rope(64)]
Value = C(512)
```

可以把它看作一个特殊的 MQA：

```text
Q：每个 head 各有一份 512+64
K：所有 heads 共享历史 C+R
V：所有 heads 共享历史 C
```

attention 结束后，每个 head 得到一个 512 维 latent 输出，再通过各自的 `Wv` 转成256维。

## DSA 怎么加入

DSA 只是在上面计算之前，给出需要读取哪些历史 `C`：

```text
全部历史 token：100K
        │
        ▼
DSA Indexer 搜索
        │
        ▼
选出 Top-2048 个位置
        │
        ▼
读取这些位置的：
C(512) + K_rope(64)
        │
        ▼
执行 absorbed MLA
```

因此完整过程是：

```text
DSA：
从100K个历史位置中选出2048个

Absorbed MLA：
不展开这2048个位置的完整 K/V，
直接用它们的 C(512)+R(64) 做 attention
```

二者的分工：

```text
DSA     决定“看哪些 token”
Absorb  决定“如何高效计算这些 token”
MLA     决定“历史信息如何压缩保存”
```

最短总结：

> 不吸收是把每个历史 `C(512)` 展开成 `K(192)` 和 `V(256)`；吸收是把 K 矩阵移到当前 Q 上，把 V 矩阵移到 attention 求和之后，因此历史 `C` 始终不展开。两者保存的 KV cache 相同。DSA 则先从所有历史 `C` 中选出 Top-2048，再交给 absorbed MLA。

```text
GPU1 检索整条 prompt 的 query
GPU2 检索整条 prompt 的 query
GPU3 检索整条 prompt 的 query

CP4：
GPU0 检索约1/4 query
GPU1 检索另外1/4 query
GPU2 检索另外1/4 query
GPU3 检索另外1/4 query
```

这部分才有明确的**减少重复计算**的机会。同时，每卡 query 数减少，相关中间张量也可以更小。代价是增加 KV 收集等通信，最终值不值得，要看 indexer 节省的时间能否覆盖通信和其他开销。

MoE 也会受数据布局影响，但不会因为 CP 就要求每卡保存全部专家：

- **TP MoE、无 A2A 的路径**：attention 输出按 token 分片；进入 MoE 前把 token 收集起来，各卡用自己的专家权重分片计算，之后再回到 token 分片。MoE 权重仍按 TP 切，但多了布局转换。
- **EP＋A2A 路径**：每卡持有一部分专家，本地 token 经过 router 后发送到专家所在卡，计算结果再返回。可以承接 CP 分片，但要支付 dispatch/combine 通信。

所以对 GLM-5.2，CP 的价值主要是**长 prompt prefill 的 query 分工，尤其减少 indexer 等复制计算，以及降低部分临时张量的大小**。它不是通用的“省权重、省全部 KV、提高所有场景吞吐”的开关。

如果你关心的是这台机器的**纯 decode 节点**，前面这种 prefill CP 的主要收益就用不上了；它还可能改变权重布局和运行配置。真正想降低 decode KV 占用，需要验证可用的 DCP/缓存分片实现。**目前不能据已有检查，给出“GLM-5.2 在本机开 CP/DCP 就会更好”的结论。**
